## 2. Separation-of-Concerns Findings

- **Route handlers building raw Mongo aggregation pipelines** instead of delegating to `reportService.ts` (which already exists and owns `getActivityCounts`). `backend/src/routes/dashboard.ts:34-36` (`EmailEvent.aggregate([...])` for per-mailbox counts), `dashboard.ts:70-73` (rule stats aggregate), `backend/src/routes/events.ts:214-215, 309-312, 353-356, 375-377, 456-458` (five separate aggregation pipelines inline in the route file, one file already 683 lines). These are business/query logic, not request/response wiring, and belong in a service (either `reportService.ts` for the dashboard ones, or a new `eventsQueryService.ts` for the events ones since they're a different domain from reports).
- **`backend/src/routes/mailbox.ts` (2163 lines) mixes Graph pagination, Redis caching, background-job kickoff, and contact de-duplication/sorting logic directly in route handlers** (e.g. the contacts endpoint at `mailbox.ts:1590-1650` inlines pagination, sorting, Redis writes, and error handling for a background sync all in one handler). This is the same file flagged for size in the file-splitting doc — the size and the concern-mixing are the same root cause here; extracting the Graph-pagination and mailbox-ownership helpers above (table rows 1 and 3) will shrink it materially as a side effect.
- **Frontend components reimplementing query/mutation wiring inline** (section 2, table rows 5-6) is the same finding from the frontend side: hooks exist as the intended seam between components and `api/*`, but 6 components skip it and import `api/*` functions + `useQuery`/`useMutation` directly. Not wrong per se (still goes through TanStack Query, not raw `fetch`), but it means query-key strings and invalidation logic are duplicated instead of centralized, so a query-key rename requires hunting across components instead of one hook file.

## 3. Typing / Error-Handling / Logging Findings

- **`any` typing** — backend has exactly 4 occurrences, all in one file: `backend/src/routes/events.ts:192` (`let events: any[]`, has an eslint-disable comment acknowledging it), `events.ts:493` (`(e as any).metadata?.isNewsletter`), `events.ts:536, 677` (`catch (err: any)`). Frontend has zero `any` usage — good baseline, don't regress it. No `@ts-ignore`/`@ts-expect-error` anywhere in the repo.
- **Missing explicit return types on exported functions** — precise check (not just grep-for-`Promise<`, which false-positives on multi-line signatures) found two files where *every* exported function lacks a return-type annotation: `backend/src/services/subscriptionService.ts:18, 80, 114, 150, 219` (`createSubscription`, `renewSubscription`, `deleteSubscription`, `syncSubscriptionsOnStartup`, `handleLifecycleEvent`) and `backend/src/services/tunnelService.ts:142, 171, 254` (`getTunnelStatus`, `refreshTunnel`, `updateTunnelUrl`). Every other service file in `backend/src/services/` already annotates return types — these two are the outliers, not the norm.
- **`console.error` instead of the shared logger** — only 2 occurrences, both in `backend/src/routes/events.ts:537, 678`, both in `catch` blocks that also use the untyped `err: any` and the flat error-shape response (finding #7 above and the `any` finding above) — same two lines, three separate issues stacked. Every other file in the codebase already uses `logger` from `backend/src/config/logger.ts` (46 files import it) — `events.ts` is the outlier.
- **Error-response shape inconsistency** — covered in table row 7. Worth calling out here too because it's a correctness risk, not just style: `frontend/src/api/client.ts:86-87` already assumes the nested `{error:{message}}` shape for CSRF-retry detection, so a flat `{error: 'string'}` response silently fails that check path (`body?.error?.message` is `undefined`, not the string) — this is a latent bug, not just an inconsistency.
- **Try/catch style is otherwise consistent and correct**: most routes rely on Express 5's native async-rejection-to-`next()` forwarding (no `try/catch` needed, confirmed via `backend/src/server.ts:100` registering `globalErrorHandler`), and the `try/catch` blocks that do exist are almost all legitimate best-effort side-operations (e.g. `rules.ts:238-243`, `patterns.ts:262-273`: sync-to-Graph or fetch-deleted-items failures are logged as `logger.warn` and swallowed on purpose, not covering up primary-path errors). `aiSearch.ts` and `health.ts` are the only files with redundant manual `try { ... } catch (err) { next(err) }` wrappers that Express 5 would already handle — low-value cleanup, not a bug.

## 4. Prioritized Refactor Plan (safest first)

| # | Item | Effort | Risk | Verification command |
|---|------|--------|------|------------------------|
| 1 | Route flat error responses (#7) through `AppError` subclasses instead of ad-hoc `res.status().json({error:'...'})` — 7 call sites, purely additive to existing infra | S | Very low — no behavior change for callers already reading `body.error` loosely; fixes a latent bug in the CSRF-retry check | `cd backend && npx vitest run` (existing suite) + manually trigger one 400 (empty AI-search query) and confirm response is `{error:{message,status,timestamp}}` |
| 2 | Replace `console.error`/`err: any` in `events.ts:536-538, 677-679` with `logger.error` + typed `err: unknown` + `err instanceof Error` narrowing | S | Very low — logging-only, same 2 lines already flagged above | `cd backend && npx vitest run` + `grep -rn "console\." backend/src` returns nothing |

**Ordering rationale:** items 1-3 are pure additive/typing fixes with no call-site migration (do first, near-zero risk). Items 4-6 are backend codemods across many call sites but mechanical and covered by the existing route test suite. Items 7-8 are the frontend equivalent, gated on query-key correctness. Items 9-10 are the highest-risk, highest-payoff items — they touch Graph API pagination (real production data, real rate limits) and reporting aggregations respectively — and should only be attempted once the lower-risk cleanups have proven the test/verification loop still catches regressions.
