# db.md — MSEDB database audit (2026-08-13)

**Engine:** MongoDB 8.2 via Mongoose 8.23, one distinct database: `msedb` on
`msedb-mongo:27017` (host port 27020, DGX, shared mongod with JTCRM's
`dailylog_db`). Prod is the only environment (accepted deviations STG-001/002/003).

**HARD CONSTRAINT HONORED:** no `ssh`, `docker`, or live DB connection was made
this run (halted per HALT LIST). Every check that needs a live catalog, live
stats, or a live orphan count is `NOT_EVALUATED` below — never guessed as PASS.
Static analysis covers all 12 Mongoose model files
(`backend/src/models/*.ts`), the routes/services/workers that query them, and
the project's own docs (`data.md`, `backup.md`, `docs/msedb-ddl.md`).

`docs/msedb-ddl.md` (committed, dated 2026-08-08, generated by the prior
`/tdbaudit` run against live prod) is treated as evidence of the last-known
live state, not re-verified live — findings sourced from it say so explicitly.

## Findings

### DB-01 · MEDIUM · db · impact M / effort M · status: OPEN
**Where:** `docs/msedb-ddl.md:26` (live snapshot of `mongodb://msedb-mongo:27017/msedb calendarsyncmaps`)
**Claim:** The `calendarsyncmaps` collection (3 indexes, incl. a unique compound
index) was still present in prod as of the 2026-08-08 DDL snapshot, but the
calendar-sync feature that owned it was removed from the codebase on
2026-04-08 (`git show 7a95f05` — "refactor: remove calendar sync — keep
email-only scope"). No file under `backend/src` references `CalendarSyncMap`
or `calendarsyncmaps` today (`git grep` returns zero hits outside an unrelated
OAuth-scope string in `msalClient.ts`). The DDL snapshot also lists a second,
index-less `settings` collection with no matching model at all — likely a
leftover, lower-priority second orphan candidate worth the same review.
**Why it matters:** Four-plus months of unowned, unretained data (likely
calendar event data — attendee emails, subjects) sitting in prod with no code
path reading, writing, or cleaning it up, and no TTL. It also still costs
index-maintenance overhead on every unrelated write to the same mongod.
**Fix:** Confirm current live document count and last-write time on
`calendarsyncmaps` (and `settings`), archive-dump if non-empty, then drop per
`db-checks.md`'s DB-ORPH-001 procedure (collision-safe rename → watch window →
drop) — never a direct DROP.
**Verifier:** `NONE — human judgment` (dropping/renaming a live prod
collection is a DB mutation; per HARD GUARD 4 this is never auto-eligible).
**Eligible for --fix:** no

### DB-02 · HIGH · db · impact H / effort L · status: OPEN
**Where:** `backend/src/routes/admin.ts:406-434` (`POST /api/admin/prefetch-unread-bodies`)
**Claim:** `EmailEvent.find({ eventType: 'arrived', isRead: false, isDeleted:
false }, { mailboxId: 1, messageId: 1 })` has no `.limit()`, no `.lean()`, and
no batching — it loads every matching document (against a collection that was
~493k docs / 408 MB as of the last live audit) into Node memory in one request,
then runs a synchronous `for` loop that `await`s a Redis `exists` check
per-document before queueing a job (an N+1 access pattern against Redis inside
a single HTTP handler).
**Why it matters:** Unbounded growth of "unread arrived" events makes this
handler's memory footprint and wall-clock time scale with the whole mailbox
backlog, not with what one admin action should touch — a request that used to
return in seconds can time out or OOM the backend as the collection grows,
and it violates the house rule "filter/aggregate/paginate in the DATABASE,
never in app code."
**Fix:** Add `.limit(N)` (e.g. 500-1000 per invocation, matching the queue's
own stagger cadence) and `.lean()` to the query in
`backend/src/routes/admin.ts`, and batch the Redis existence checks
(`redis.exists` pipeline / `mget`-style) instead of one `await` per document.
**Verifier:** `grep -A6 "EmailEvent.find(" backend/src/routes/admin.ts | grep -q "\.limit("`
(exits 1 today — confirmed; exits 0 once a `.limit(` is added to that call)
**Eligible for --fix:** yes

### DB-03 · MEDIUM · db · impact M / effort L · status: OPEN
**Where:** `backend/src/models/AuditLog.ts:12` (enum `pattern_unapproved` added), `data.md` (## DB change log)
**Claim:** Commit `b17a29d` (2026-08-13, today) added a new `AuditLog.action`
enum value (`pattern_unapproved`) — a schema change (Mongoose validates enum
membership at write time, so this is a real shape change to an existing
collection). `data.md`'s `## DB change log` table has exactly one row, dated
2026-08-08, and does not mention this change.
**Why it matters:** The project's own house rule states "every schema or data
change — including manual/ad-hoc edits — gets a row" in `data.md`; this is the
*only* change-tracking mechanism MSEDB has (there is no migration framework —
see DB-05), so an unlogged schema change is now effectively invisible to
anyone auditing what changed and when.
**Fix:** Append a row to `data.md`'s `## DB change log` table for the
`pattern_unapproved` enum addition, referencing commit `b17a29d`.
**Verifier:** `grep -q "pattern_unapproved" data.md` (exits 1 today — confirmed; exits 0 once the row is added)
**Eligible for --fix:** yes

### DB-04 · MEDIUM · db · impact M / effort M · status: OPEN
**Where:** `backend/src/routes/rules/crud.ts:341` and `:409` (`Rule.deleteOne`), `backend/src/models/StagedEmail.ts:12` (`ruleId: { ..., required: true }`)
**Claim:** Both rule-delete paths (`POST /delete-by-sender` and `DELETE
/:id`) call `Rule.deleteOne({ _id: rule._id })` with no corresponding cleanup
of `StagedEmail` documents whose `ruleId` still points at the deleted rule.
`StagedEmail.ruleId` is a required `ObjectId` ref to `Rule` with no default and
no cascade. (Execution itself doesn't break — `stagingProcessor.ts` reads the
staged item's own embedded `actions`, not the rule — but the reference goes
stale and any future code or admin query that dereferences `StagedEmail.ruleId`
via `.populate()` will silently get `null`.)
**Why it matters:** This is exactly the shape of orphan risk the standing
referential-integrity check looks for; the last live orphan check
(2026-08-08, before this feature's most recent edits) reported zero orphans,
but nothing in the code path prevents a new one from being created every time
a user deletes a rule while a matching staged email is still pending.
**Fix:** In both delete handlers in `backend/src/routes/rules/crud.ts`, either
cancel/expire (`status: 'expired'`) or delete any `StagedEmail` with `status:
'staged'` and `ruleId: rule._id` before/after the `Rule.deleteOne` call.
**Verifier:** `grep -q "StagedEmail" backend/src/routes/rules/crud.ts`
(exits 1 today — confirmed; exits 0 once the cleanup call is added)
**Eligible for --fix:** yes

### DB-05 · MEDIUM · db · impact M / effort H · status: OPEN
**Where:** `data.md` (## Migrations section)
**Claim:** `data.md` itself states: "**None. There is no migration framework
in this project.** Mongoose applies schema shape at write time... collection
changes today happen implicitly when a model file changes." Confirmed: no
`backend/src/migrations/` directory, no `migrate-mongo` (or equivalent) in
`backend/package.json`.
**Why it matters:** Per the Per-App Standard, "every DB change = versioned
migration + data.md log row" — MSEDB currently only has the second half (and
even that has gaps, see DB-03). Every schema change is an untracked, ad-hoc
edit to a model file with no record of what ran, when, or whether it was
applied consistently against the one live database.
**Fix:** Adopt a lightweight migration mechanism (e.g. `migrate-mongo`, or a
small in-repo `backend/src/migrations/` runner invoked at startup, both
already named as candidates in `data.md`) — this is an architecture decision
for Taj to make, not an autonomous change.
**Verifier:** `NONE — human judgment` (framework choice; this is already
self-documented as an open gap, not a hidden one)
**Eligible for --fix:** no

### DB-06 · LOW · db · impact L / effort L · status: OPEN
**Where:** `backend/src/models/Mailbox.ts:88-89`
**Claim:** `mailboxSchema.index({ userId: 1, email: 1 }, { unique: true })` is
immediately followed by `mailboxSchema.index({ userId: 1 })`. The second index
is a strict prefix of the first (unique) compound index — any query filtering
only on `userId` (and there are several: `mailbox/connection.ts:72`,
`settings.ts:31/68`, etc.) is already served by the compound index's leading
field, per MongoDB's prefix rule.
**Why it matters:** A redundant index costs write amplification and storage
on every `Mailbox` insert/update for zero query benefit — small collection
today (per-user mailbox count is low), but it's free to remove and is exactly
the DB-IDX-002 pattern the standing index-hygiene check looks for.
**Fix:** Delete the standalone `mailboxSchema.index({ userId: 1 });` line in
`backend/src/models/Mailbox.ts`.
**Verifier:** `! grep -q "userId: 1 });$" backend/src/models/Mailbox.ts`
(exits 1 today — confirmed the redundant line is present; exits 0 once it's removed)
**Eligible for --fix:** yes
